# Production Readiness Audit Design

The production-readiness audit will be implemented as a **standalone Python program** that performs a repository-wide static assessment and produces both **machine-readable JSON** and **human-readable Markdown** outputs. The audit will not rely on a single narrow checklist. Instead, it will combine **inventory analysis**, **pattern-based code inspection**, **configuration discovery**, and **weighted domain scoring** so the repository can be evaluated consistently in local development, pre-merge validation, and deployment pipelines.

The script will inspect the repository recursively and classify files into source code, tests, infrastructure, documentation, automation, mobile, ML, and generated artifacts. For code-bearing files, it will extract lightweight structural signals such as **functions**, **methods**, **classes**, **interfaces**, **route declarations**, **API handlers**, **environment variable usage**, **security middleware references**, **tests**, **TODO/FIXME markers**, and **integration client patterns**. The aim is to provide coverage-like evidence for implementation surfaces without pretending to execute business logic.

The scoring model will be divided into seven weighted domains. The first domain will assess **feature completeness** by comparing the discovered user-facing surfaces such as pages, routes, components, service modules, API routers, and tests. The second domain will assess **code implementation quality** using indicators like typed code presence, test density, unresolved placeholders, mocks in production code, and dead or thin modules. The third domain will assess **service and integration readiness** by identifying external integrations, service directories, environment-bound clients, queues, messaging, and background jobs. The fourth domain will assess **security readiness** through discovery of authentication, authorization, CSRF, rate limiting, secret management patterns, hardcoded credential smells, and dependency audit outputs. The fifth domain will assess **infrastructure and operations** readiness by discovering Docker assets, Kubernetes files, deployment manifests, health checks, observability, rollback patterns, and environment examples. The sixth domain will assess **delivery pipeline maturity** by reviewing GitHub Actions, build steps, test stages, security stages, artifact handling, and deploy gates. The seventh domain will assess **documentation and maintainability** by checking README-like assets, example environment files, runbooks, operational scripts, and consistency between scripts and pipeline definitions.

Each domain will be composed of explicit **checks** with IDs, descriptions, weights, score values, evidence excerpts, and recommendations. Checks will be evaluated from repository evidence rather than hardcoded assumptions about a specific stack. For example, the audit can award points when authentication middleware, health endpoints, environment examples, CI workflows, or deployment manifests are present, and it can reduce points when unresolved TODO markers, placeholder secrets, missing tests, or undocumented services are detected. The final output will include an **overall completeness score**, **domain-level scores**, **failed checks**, **warning checks**, **inventory metrics**, and **top remediation priorities**.

The audit output will support both standalone and CI/CD use. In standalone mode, the script will be runnable directly with Python and will emit reports into a target directory. In CI/CD mode, the script will support configurable failure thresholds, strict mode, and machine-readable status so that pull requests or deployment stages can be blocked when readiness drops below a required minimum. A small JSON configuration file will define weights, ignored directories, extensions, thresholds, and keyword patterns so the audit remains maintainable as the repository evolves.

The implementation will therefore include four concrete deliverables. The first will be the main Python audit program under `scripts/`. The second will be a repository-local JSON configuration file under `scripts/` so weights and exclusions can be tuned without editing code. The third will be package and Makefile integration for local use. The fourth will be GitHub Actions integration that runs the audit after build validation and uploads the generated reports as workflow artifacts.
